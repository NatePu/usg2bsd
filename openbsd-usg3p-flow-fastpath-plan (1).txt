OPENBSD/OCTEON CN50xx FLOW FAST PATH -- FORK PLAN (LAB / NON-PRODUCTION)
=========================================================================

Target hardware : Ubiquiti UniFi Security Gateway 3P (USG-3P) only.
                  Cavium CN5020, two cnMIPS64 cores at 500 MHz, 512 MB
                  RAM, three RGMII ports (cnmac0..2), no FPU, 128 KB L2,
                  internal USB flash drive holding the OS.
Base             : OpenBSD -current (octeon), private fork.
Ground rules     : This is a fork. It will not be merged upstream. We may
                   change struct layouts, add compile-time hooks, panic on
                   invariant violations, hardcode everything to the
                   USG-3P (CN5020, three ports, two cores), and skip man
                   pages, regress and review etiquette. No other board is
                   in scope. Correctness matters only as far as the lab
                   router must forward packets reliably for days.
Reference impl.  : OpenWrt PR #25645 (markusdd, Oct 2026), "forward
                   established flows on CN50xx", plus sibling PR #25823
                   (bridged traffic). Measured on a real USG-3P:
                     no offload           89-116 Mbit/s
                     software flowtable  561-602 Mbit/s
                     shortcut (NAT)      941/934 Mbit/s
                     shortcut PPPoE+VLAN  ~930 Mbit/s
                     shortcut routed v6  902-913 Mbit/s
                     64-byte UDP          ~145 kpps
                     both LAN ports       ~952 Mbit/s combined
OpenBSD baseline : 172 Mbit/s terminating with pf, 229 without
                   (USG-3P, -current 2025), one core at 100% in softnet.
                   No published routed-NAT number for the USG-3P exists;
                   step 7 measures it.


1. WHAT "HARDWARE OFFLOAD" MEANS ON THIS CHIP
--------------------------------------------

The CN5020 has no flow engine (nothing like MediaTek's PPE). The Linux
"shortcut" is CPU code in the Ethernet driver's receive loop that:

  - trusts the hardware parser (PIP) for L3/L4 offsets, fragment flag
    and checksum verdicts delivered in the work-queue entry (WQE);
  - looks the 5-tuple up in a flow table;
  - rewrites headers in place in the DMA buffer (FPA packet pool);
  - hands the same buffer to the packet output unit (PKO), which
    recomputes the L4 checksum (IPOFFP1) and frees the buffer back to
    the pool after transmit (DF=0);
  - never allocates an skb, never enters the IP stack, never crosses a
    thread.

The 145 kpps ceiling at 64 bytes proves it is CPU-bound. Nothing needs
the Ubiquiti blob. The same design is possible on OpenBSD; the hard parts
are the control plane (pf integration) and buffer ownership, not the
hardware.


2. HARDWARE FACTS TO BUILD ON (verify field names in sys/arch/octeon/dev)
-----------------------------------------------------------------------

WQE (4 x 64-bit words, from cn30xxpipreg.h / if_cnmac.c usage):
  word0  POW tag, tag type, group, next pointer. Not needed on hit.
  word1  PIP_WQE_WORD1_LEN (bits 63..48) packet length
         PIP_WQE_WORD1_IPRT (bits 47..42) input port
  word2  PIP_WQE_WORD2_IP_BUFS   number of packet buffers (must be 1)
         PIP_WQE_WORD2_NOIP_RE   receive error (+ opcode)
         PIP_WQE_WORD2_IP_NI     not IP (set for PPPoE frames)
         PIP_WQE_WORD2_IP_V6     IPv6
         PIP_WQE_WORD2_IP_IE     IP header checksum error
         PIP_WQE_WORD2_IP_TU     L4 is TCP or UDP
         PIP_WQE_WORD2_IP_FR     fragment
         PIP_WQE_WORD2_IP_LE     L4 checksum error
         also (Cavium layout, check header): ip_offset (8 bits),
         vlan_valid, vlan_id (12 bits), is_bcast, is_mcast.
  word3  PIP_WQE_WORD3_ADDR  physical address of packet data
         PIP_WQE_WORD3_BACK  cache lines back to the buffer start
         size field is unreliable (erratum PKI-100), compute from
         OCTEON_POOL_SIZE_PKT as cnmac_recv_mbuf() does.

FPA pools (if_cnmac.c): OCTEON_POOL_NO_WQE, _CMD, _SG, _PKT.
  Packet buffers are ordinary mbuf clusters pre-registered into the PKT
  pool by cnmac_mbuf_alloc(); the mbuf pointer is stashed at
  m_data[-1] (8 bytes before the buffer start). The pool, not the
  driver, owns a buffer until the WQE arrives. This is what lets PKO
  return a buffer to the pool after transmit without software help.

POW: one group per port (sc_powgroup), interrupt POW_WORKQ_IRQ(group),
  IPL_NET|IPL_MPSAFE, work fetched with cn30xxpow_work_request_async /
  work_response_async. Since if_cnmac.c 1.65 each port's interrupt is
  bound to a CPU, so cnmac0 and cnmac1 fast paths run on different cores
  naturally.

PKO (cn30xxpko.c, "assume one queue mapped one port"):
  command word0 = cn30xxpko_cmd_word0(sz1, sz0, s1, reg1, s0, reg0, le,
                  n2, q, r, g, ipoffp1, ii, df, segs, totalbytes)
     reg0/s0    FAU register updated on completion (driver: sc_fau_done)
     g          gather mode
     ipoffp1    IP header offset + 1; nonzero makes PKO compute the
                TCP/UDP checksum (driver already uses ETHER_HDR_LEN+1)
     df         don't free. Driver uses df=1 and frees mbufs itself from
                the FAU completion count. Fast path will use df=0.
  command word1 = cn30xxpko_cmd_word1(i, back, pool, size, addr)
  Commands are written into a per-port command buffer (sc_cmdptr, CMD
  pool), then cn30xxpko_op_doorbell_write(port, queue, 2).

FAU: per-port completion counter sc_fau_done drives TX garbage
  collection in cnmac_send_queue_flush().

Memory ordering: packet buffer writes must be visible to PKO before the
  doorbell (mips_sync / SYNCW, see cn30xxpko.c).

Headroom: cnmac_ipd_init() sets first_mbuff_skip = 0 and the driver sets
  sc_ip_offset = 0 ("setting 8 panics"), so there is essentially no
  headroom in front of the frame. VLAN (+4) or PPPoE (+8) insertion
  needs an IPD skip change (section 6, step 23).


3. CURRENT OPENBSD DRIVER FLOW (if_cnmac.c) AND WHERE WE HOOK
------------------------------------------------------------

RX: cnmac_intr()
      loop: work = cn30xxpow_work_response_async()
            check port == sc->sc_port
            cnmac_recv(sc, work, &ml)
               cnmac_recv_check()      error WQEs
               cnmac_recv_mbuf()       returns WQE to pool, builds mbuf
                                       chain from stashed pointers,
                                       clears the stash (*pm = NULL)
               csum flags from word2
      if_input(ifp, &ml)               -> softnet thread (the bottleneck)
      refill: cnmac_mbuf_alloc(nmbuf)  one new cluster per consumed one

    HOOK A: between "port check" and cnmac_recv(): try the fast path on
            the raw WQE. On hit the WQE is consumed and nmbuf is NOT
            incremented (the buffer comes back via PKO).

TX: cnmac_start(ifq)  [runs under the ifq serializer]
      cnmac_send() -> SG buffer -> cnmac_send_makecmd() ->
      cnmac_send_cmd() [per-port command buffer, no lock] -> sendq
      completions: FAU counter -> cnmac_send_queue_flush() -> m_freem

    HOOK B: in cnmac_start() before cnmac_send(): if the mbuf carries a
            flow candidate record, learn the flow from the final frame.
    HOOK C: cnmac_send_cmd() must become callable from another port's
            interrupt (lock or dedicated queue).

pf (sys/net/pf.c): pf_test() runs twice per forwarded packet, PF_IN on
  the ingress interface and PF_OUT on the egress interface, and a
  normal ruleset creates TWO states per flow (one per rule). Both must
  be eligible, both must be kept alive, and removal of either tears the
  flow down. Translation lives in the state keys:
     key[PF_SK_WIRE]   addresses as seen on the wire of that interface
     key[PF_SK_STACK]  addresses after translation
  Established detection: TCP src.state and dst.state >= TCPS_ESTABLISHED
  (pf_tcp_track_full); UDP state PFUDPS_MULTIPLE.


4. DESIGN (FORK EDITION)
------------------------

4.1 Components

  sys/net/if_flow.c, if_flow.h   flow table, learn, teardown, GC, sysctl,
                                  kstat, ddb printer. SMR for readers,
                                  one mutex for writers. Style model:
                                  sys/net/if_etherbridge.c (veb).
  sys/net/pf.c, pfvar.h           direct calls into if_flow (fork: no
                                  function-pointer registry needed).
                                  New fields in struct pf_state.
  sys/sys/mbuf.h                  two extra pointers in struct pkthdr_pf
                                  for the candidate record (fork: fine).
  sys/arch/octeon/dev/if_cnmac.c  hooks A/B/C, zero-copy hit path,
                                  PKO lock or extra queue, FPA free-count
                                  kstats, headroom change.
  sbin/pfctl                      print "offloaded" in -vvss (optional).

4.2 Data structures (sketch)

  struct flow_key {
      u_int16_t  ifidx;        /* physical ingress cnmac */
      u_int16_t  rdomain;
      u_int16_t  vlan;         /* 0 = untagged */
      u_int16_t  pppoe_sess;   /* 0 = none */
      u_int8_t   af, proto;
      u_int16_t  sport, dport;
      union { struct in_addr v4[2]; struct in6_addr v6[2]; } addr;
  };

  struct flow {
      SMR_LIST_ENTRY(flow)  f_hash;
      struct flow_key       f_key;        /* ingress tuple (pre-rewrite) */
      struct ifnet         *f_egress;     /* physical cnmac */
      u_int8_t              f_l2[32];     /* learned egress L2 template:
                                             dst MAC, src MAC, optional
                                             802.1Q, optional PPPoE+PPP */
      u_int8_t              f_l2len;      /* 14, 18, 22, 26 */
      u_int8_t              f_in_l2len;   /* ingress L2 length */
      u_int8_t              f_flags;      /* DEAD, V6, PPPOE_OUT, ... */
      union { ... } f_naddr[2];           /* new src/dst */
      u_int16_t             f_nport[2];   /* new src/dst port */
      u_int32_t             f_csum_delta; /* precomputed RFC1624 delta */
      struct pf_state      *f_st[2];      /* in-state, out-state (either
                                             may be NULL) */
      u_int64_t             f_pkts, f_bytes, f_pkts_gc, f_bytes_gc;
      time_t                f_lastuse;
      struct smr_entry      f_smr;
  };

  struct pf_state gains:  struct flow *flows[2]; (fwd, rev)
  struct pkthdr_pf gains: struct pf_state *flowcand[2]; (set at PF_IN
                          and PF_OUT), plus a PF_TAG_FLOWCAND bit, plus
                          the ingress ifidx recorded at PF_IN.

4.3 Control flow

  Learn (slow path, first packets of a flow):
    pf_test(PF_IN): state found, eligible, established -> set
        m->m_pkthdr.pf.flowcand[0] = s, record ingress ifidx, set tag.
    pf_test(PF_OUT): same -> flowcand[1] = s.
    cnmac_start(): tag set -> flow_learn(ifp, m):
        - walk the final frame's L2 (ethertype 0x8100 -> +4, 0x8864 ->
          +8 incl. PPP proto) to the IP header;
        - expected egress tuple = out-state WIRE key if present, else
          in-state STACK key. If the frame's tuple differs (IPsec, gif,
          gre, wg, NAT64...), do NOT learn, count "refused_mismatch";
        - ingress tuple = in-state WIRE key (or out-state STACK key);
        - ingress L2: resolve the PF_IN interface: vlan(4) -> parent +
          tag, pppoe(4) -> parent + session, else physical;
        - insert flow; point s->flows[dir] at it for both states.
    The reverse direction learns on its own when the reply leaves the
    other port. Each direction is an independent flow entry.

  Hit (fast path, in cnmac_intr, before cnmac_recv):
    pre-checks on word2: !NOIP_RE, IP_BUFS==1, !IP_FR, !IP_IE, !IP_LE,
        !bcast, !mcast; IP_NI allowed only when PPPoE parsing is on.
    pkt = PHYS_TO_XKPHYS(word3.addr); len = word1.len
    find IP header: word2.ip_offset, or software walk for PPPoE.
    v4: ihl == 5, ttl > 1; v6: next header TCP/UDP, hlim > 1.
    TCP: th_flags & (SYN|FIN|RST) -> slow path (pf must see them).
    key = {ifidx, rdomain, vlan, pppoe, af, proto, addrs, ports}
    smr_read_enter(); f = lookup(key); if !f or DEAD -> slow path.
    egress link up; len - f_in_l2len + f_l2len <= egress MTU + L2;
    bpf listener on ingress or egress -> slow path (keeps tcpdump sane).
    reserve a PKO command slot on egress FIRST (lock), so a failure
        leaves the packet untouched and it can fall to the slow path.
    rewrite:
        new data ptr = pkt + f_in_l2len - f_l2len (needs headroom when
            f_l2len > f_in_l2len); copy f_l2 template;
        v4: addrs, ttl--, ip_sum incremental; v6: addrs, hlim--;
        ports; L4 checksum: PKO via ipoffp1 = f_l2len + 1 (fallback:
            incremental update in software using f_csum_delta);
        PPPoE out: length field = ip_len + 2.
    word0: g=0, segs=1, totalbytes=newlen, ipoffp1, df=0, no FAU
        (reg0=reg1=0 -- verify "0 means none"), word1: pool=PKT,
        back recomputed from the new data pointer, size=newlen.
    mips_sync(); write cmd; doorbell.
    smr_read_leave(); return WQE to the WQE pool; bump f_pkts/f_bytes;
    counters_pkt() ipackets/ibytes on ingress, opackets/obytes on
    egress. Do not touch the mbuf stash at buffer-8; PKO returns the
    buffer to the pool and the next RX reuses the same mbuf.

  Teardown:
    pf_remove_state(s): for both s->flows[]: set DEAD under the flow
        mutex, unlink from hash, clear the other state's pointer,
        smr_call() free. Happens before pf_free_state(), so f_st[]
        pointers never dangle for the GC.
    pf_tcp_track_full(): when either peer leaves ESTABLISHED (FIN/RST
        seen on the slow path), same teardown. pf then handles the
        remaining packets of the close normally.
    pfctl -F states / ruleset reload: covered by pf_remove_state.

  Refresh (keeps pf timers and counters honest):
    timeout every 1 s: for each flow with f_pkts != f_pkts_gc:
        for each f_st[i] != NULL: mtx_enter(&s->mtx);
        s->expire = getuptime(); s->packets[dirndx] += delta;
        s->bytes[dirndx] += delta; mtx_leave. dirndx is 0 when the flow
        direction equals s->direction, else 1.
    pflow export on removal then carries sane counters.

4.4 Locking and MP

  - lookup: SMR read section only; no allocation; runs at IPL_NET
    MPSAFE in the ingress port's interrupt on its own core.
  - insert/remove: flow mutex (IPL_NET); learn runs in cnmac_start
    (ifq serializer context), teardown runs from pf under NET_LOCK.
  - PKO submission from a foreign core: per-port sc_pko_mtx around
    command-buffer write + doorbell in BOTH normal and fast paths, OR a
    dedicated PKO queue per egress port for the fast path with its own
    command buffer (preferred if CN50xx has spare queues; keeps the ifq
    path untouched and lock-free). Decide in step 5.
  - flow counters are written by one core (ingress port is fixed) and
    read by the GC; use atomic adds or accept small skew.

4.5 Knobs and observability (fork-simple, no pf.conf syntax)

  sysctl net.flow.mode      0 off, 1 software hit path (debug), 2
                            zero-copy, 3 shadow (lookup + counters,
                            no shortcut; validates control plane)
  sysctl net.flow.max       table size (refuse on full, no eviction
                            needed in the lab)
  sysctl net.flow.gc        refresh interval, seconds
  sysctl net.flow.pppoe     enable PPPoE parsing (phase 3)
  sysctl net.flow.policy    0 = offload every eligible state (default
                            for the fork), 1 = only states whose rule
                            has a marker tag (reuse pf "tag" keyword,
                            e.g. tag OFFLOAD, so no parser change)
  kstat cnmacN:0:flow       hits, misses, learned, refused_*, dead_hits,
                            pko_full, slow_tcpflags, slow_frag, ...
  kstat cnmacN:0:fpa        free count per FPA pool (leak detector:
                            FPA_QUEx_AVAILABLE registers)
  ddb: "show flows", "show flow <addr>"
  pfctl -vvss: print "offloaded" when s->flows[] non-NULL (optional)

4.6 Eligibility (refuse to offload if any applies)

  state_flags/rule: PFSTATE_SLOPPY is fine; refuse modulate state
  (seqdiff != 0), synproxy, af-to, route-to/reply-to/dup-to,
  divert-*, queue / set prio / set delay (zero-copy mode only; the
  software mode can honour qid/prio), log (all), min-ttl, set tos,
  scrub no-df/random-id (or implement no-df: trivial). Interface is a
  veb/bridge member -> refuse. Non-cnmac egress -> refuse. af != inet /
  inet6, proto != TCP/UDP -> refuse.

4.7 Deliberately unsupported in the fork
  fragments, ICMP/ICMPv6, multicast, IP options, v6 extension headers,
  multi-buffer (jumbo) frames, ESP/GRE pass-through states, flows that
  terminate on the router, pfsync peers staying in sync for offloaded
  flows (use "sloppy" on failover pairs or don't offload), QoS in
  zero-copy mode, tcpdump of offloaded packets (we fall back instead).


5. REQUIREMENTS CHECKLIST
-------------------------

Must
  R1  Forward established TCP/UDP, IPv4 and IPv6, between cnmac ports
      without softnet, pf or ip_forward on the hit path.
  R2  Apply pf's translation exactly as the state keys describe; TTL
      and hop-limit decrement; correct IPv4 header and L4 checksums.
  R3  Offload only when every traversed state is eligible and
      established; tear down on removal, timeout or leaving ESTABLISHED.
  R4  Refresh pf expire and counters for offloaded flows.
  R5  Slow path for everything in 4.7 plus SYN/FIN/RST, TTL<=1,
      checksum errors, MTU exceeded, PKO/command exhaustion, bpf
      listeners.
  R6  Never offload a flow whose egress frame does not match the
      expected post-translation tuple (IPsec/tunnel guard).
  R7  No allocation and no locks other than SMR on the hit path.
  R8  Buffers always return to the FPA pool; FPA free counts are
      observable; a leak is detectable within minutes.
  R9  Feature fully disabled by net.flow.mode=0 with no residual
      behaviour change.
Should
  R10 Zero-copy mode: >900 Mbit/s NAT, >100 kpps at 64 bytes, both
      ports concurrently.
  R11 Software mode: 400-600 Mbit/s; used to validate the control plane
      and as the debug fallback.
  R12 VLAN and PPPoE encapsulation on either side, as in the Linux PR.
Won't
  R13 Upstream-cleanliness, generic driver API, support for any board
      other than the USG-3P, pf.conf syntax, regress tests beyond lab
      scripts.

Licensing note: the OpenWrt patch is GPL. For a private lab fork,
reading it as a reference is fine. If the fork is ever published, keep
anything derived from it clearly marked and separate; everything else is
written against OpenBSD's BSD-licensed IIJ headers and the BSD-licensed

6. STEPS
--------

Phase 0 -- bench, build loop, hardware verification
  1.  Check out OpenBSD -current; snapshot the exact tree (fork point).
      Read if_cnmac.c, cn30xxpko.c, cn30xxpip*.h, cn30xxipd*.h,
      cn30xxfpa*.h, cn30xxpow*.h and confirm the RX/TX structure in
      section 3 still holds.
  2.  Read pf.c/pfvar.h/pf_norm.c and write down: state struct fields,
      pf_test() state-match path, where expire/packets/bytes are
      written and under which lock, pf_remove_state()/pf_free_state()
      ordering, pf_tcp_track_full() transitions, how qid/prio are put
      on packets, whether pf_mbuf_link_state_key() runs for forwarded
      packets.
  3.  Read if_etherbridge.c and kern_smr.c (SMR table pattern), ifq.c
      (serializer rules), if_vlan.c and if_pppoe.c (parent/tag/session
      fields needed by learn).
  4.  Collect the Cavium references listed above; keep a reading log.
  5.  Verify on hardware, with throwaway kernels:
      a. PKO df=0 with pool=PKT and a recomputed "back" frees the
         buffer to the pool and the stashed mbuf pointer survives;
      b. reg0=0 really means "no FAU update";
      c. number of PKO queues available per port on CN50xx (decide
         lock vs dedicated queue, 4.4);
      d. PIP word2 vlan_valid/vlan_id and ip_offset semantics;
      e. PIP does not parse IP inside PPPoE (expect IP_NI set);
      f. headroom currently available in front of the frame;
      g. ipoffp1 checksum works for IPv6 and for offsets 18/22/26.
  6.  Build loop: cross-build the octeon kernel on amd64
      (Makefile.cross, TARGET=octeon); native builds on the USG itself
      are possible but take hours, keep them for overnight runs. Boot
      kernels over TFTP from U-Boot (dhcp; tftpboot 0 bsd; bootoctlinux
      rootdev=/dev/sd0 numcores=2) so the internal USB stick is never
      touched; serial at 115200. Keep a known-good "bsd.good" on the
      stick and a dd image of the original stick.
  7.  Bench scripts: iperf3/tcpbench TCP at 1500 B; pktgen/trafgen host
      for 64-byte UDP; dual-port concurrent test; capture kstat, top -S,
      systat ifstat. Establish the USG-3P baselines: terminating
      (expect ~172/229 Mbit/s) and routed NAT (unknown, measure).

Phase 1 -- control plane + software hit path (debug mode)
  8.  Add if_flow.c/.h: key, hash (jenkins or murmur over the key),
      SMR_LIST buckets, lookup/insert/remove, mode/max/gc sysctls,
      kstats, ddb printer.
  9.  Grow struct pf_state (flows[2]) and struct pkthdr_pf
      (flowcand[2], ingress ifidx, PF_TAG_FLOWCAND). Reset the record
      in m_pkthdr init paths and pf_pkt_addr_changed().
  10. pf_state_offloadable(s): implement 4.6 as a single predicate with
      a counter per refusal reason.
  11. pf_test(): after a successful state match and PF_PASS, when
      eligible and established, fill the candidate record (PF_IN slot
      on ingress, PF_OUT slot on egress).
  12. flow_learn(): called from cnmac_start() for tagged mbufs. Parse
      the final frame, verify the egress tuple against the expected key
      (R6), build the ingress key from the PF_IN interface (vlan/pppoe
      resolution), insert, link s->flows[].
  13. Teardown hooks in pf_remove_state() and pf_tcp_track_full().
  14. GC timeout: refresh expire/counters (4.3), free DEAD entries via
      smr_call, expire flows whose states vanished (belt and braces).
  15. Shadow mode (mode=3): run the lookup in cnmac_intr on the raw WQE
      and count hits/misses but take no action. Compare hit counts with
      pf state packet counters to validate keys and learn logic before
      any packet is diverted.
  16. Software hit path (mode=1): after cnmac_recv_mbuf(), lookup,
      rewrite in the mbuf, set csum_flags (PKO does L4), set pf.qid /
      prio from the state so queueing still works, ifq_enqueue on the
      egress ifp, skip if_input. Measure. Also serves as the fallback
      when zero-copy cannot handle a case.
  17. Correctness pass: NAT both directions, rdr-to, two-state flows,
      pfctl -F states under load, ruleset reload, FIN and RST close,
      UDP idle timeout, gif/wg/IPsec never learned, tcpdump present ->
      slow path, pfctl -vvss counters move, pflow export sane.

Phase 2 -- zero-copy Octeon path
  18. HOOK C: either add sc_pko_mtx around cnmac_send_cmd() (and take
      it in cnmac_start too) or implement a second PKO queue per port
      with its own CMD buffer and doorbell for the fast path. Also add
      a "reserve slot" step so failure precedes the rewrite.
  19. Implement flow_rx_fast() per 4.3 inside cnmac_intr (HOOK A),
      word2 pre-checks, software L2 walk, in-place rewrite, word0/word1
      construction with df=0 and recomputed back, SYNCW, doorbell, WQE
      return, counters. Do not increment nmbuf on hit.
  20. FPA free-count kstats (R8). Soak test for hours watching them;
      any drift means a leak in the df=0 path.
  21. Measure 1500 B and 64 B, single and dual port, NAT and plain
      routing, v4 and v6. Compare with the Linux PR table. Profile with
      the kstat counters; tune hash size and bucket count; consider
      prefetching the packet buffer right after the WQE arrives.
  22. Confirm the slow path still works for every excluded case while
      zero-copy is on (SYN/FIN/RST, fragments, ICMP, TTL=1, oversize).

Phase 3 -- encapsulations and IPv6 details
  23. Headroom: set IPD first_mbuff_skip to 64 or 128 bytes in
      cnmac_ipd_init(); verify cnmac_recv_mbuf's back/addr arithmetic
      and refill still work; re-run all RX tests. Needed for VLAN
      (+4) and PPPoE (+8) insertion in place.
  24. VLAN: key includes ingress vlan_id from word2; egress template
      learned through vlan(4) (cnmac has no hw tagging, so the tag is
      inline at the driver); ipoffp1 += 4. Test tagged<->untagged and
      tagged<->tagged with different VIDs.

9. RISKS AND OPEN QUESTIONS
---------------------------

  - df=0 on mbuf-backed pool buffers (step 5a). If PKO cannot free
    correctly, fall back to df=1 with a fast-path sendq drained by a
    second FAU counter.
  - PKO queue availability (5c). If only one queue per port, the mutex
    approach adds a little contention on the egress port's own TX.
  - Two-state teardown/refresh races: state removed while a hit is in
    flight. SMR + DEAD flag + "remove before free" ordering handles it;
    DIAGNOSTIC checks will tell.
  - IPD headroom change (23) affects all RX; keep it behind a knob
    until proven.
  - PIP ip_offset when VLAN tagged, and whether PIP sees double tags:
    treat anything unexpected as slow path.
  - Flow table under a port scan: thousands of short UDP states; cap
    with net.flow.max and only learn after PFUDPS_MULTIPLE.
  - Packet-rate ceiling: ~150 kpps is the realistic target on this
    silicon; do not expect line rate at 64 bytes.

APPENDIX A -- TECHNICAL REVIEW (2026-10-28)
==========================================================================

Review scope: USG-3P / CN5020 only; OpenBSD -current private lab fork.
Disposition : CONDITIONAL APPROVAL. Proceed with hardware verification and
              shadow-mode work, but revise the design before implementing
              pf integration and zero-copy forwarding.

This appendix records the technical review of the plan above. It does not
modify the original requirements, steps, or reference measurements. Findings
about OpenBSD -current should be rechecked against the exact commit selected
in Phase 0, because the driver and pf internals are moving targets.

A.1 OVERALL ASSESSMENT
---------------------

The proposed architecture is technically plausible. The CN5020 does not have
an autonomous hardware flow engine; this is a CPU-assisted fast path that
uses the chip's PIP/IPD/POW receive processing, FPA buffer management, and
PKO transmit hardware to avoid mbuf allocation and the OpenBSD forwarding
stack on established-flow hits. Calling it hardware-assisted fast-path
forwarding is more precise than CPU-free hardware offload.

Keep the overall architecture: pf remains the policy/state control plane;
exception packets and misses take the ordinary stack; eligible established
flows can use a driver-level shortcut. The four-phase rollout, shadow mode,
software forwarding mode, BPF fallback, per-reason refusal counters, FPA
pool observability, TFTP development boot, and recovery image are all
valuable decisions.

The primary risks are correctness of packet-buffer ownership, pf state
lifetime, forwarding-path invalidation, and multiprocessor synchronization,
not whether the chip can move packets quickly. Reported OpenWrt shortcut
throughput near 940 Mbit/s is a useful reference, but not an OpenBSD result
or a guarantee for this fork.

A.2 REQUIRED DESIGN CHANGES
---------------------------

FINDING 1 -- OpenBSD -current RX dispatch is not necessarily per-port CPU
             ownership [HIGH]
  Affects: sections 2, 3, 4.4; Phase 0 step 5; per-flow counters.

  The assumption that each cnmac physical port owns one POW group and thus
  naturally runs on only one CPU needs updating. Changes in 2026 introduced
  multiple RX queues with shared POW-group processing, dispatching work by
  physical input port after WQE retrieval. Verify cnmac_rx_groups, work-group
  setup, PIP tagging, and actual interrupt/CPU affinity in the fork point.

  Required design:
    - Hook the fast path at the actual shared RX-group receive-loop site,
      after resolving the physical port/interface.
    - Do not assume a single writer to flow counters or flow metadata
      merely because an ingress interface is fixed.
    - Use atomic/per-CPU counters and explicitly test inter-CPU ordering
      when flows transition between the fast and slow paths.

FINDING 2 -- RX WQE / mbuf / FPA / PKO ownership must be proved separately
             [HIGH]
  Affects: sections 2, 4.3; Phase 0 step 5a; Phase 2 steps 19-20.

  PKO df=0 returning an RX packet buffer to the FPA pool is the most fragile
  device-level operation. The current driver reconstructs mbuf ownership
  using the WQE data address, the 'back' value, and the mbuf-pointer stash.
  Check every assumption after moving the frame start for rewritten L2
  headers. A successful packet transmission is not proof of correct reuse.

  Required proof obligations:
    1. PKO returns exactly the originally allocated packet-buffer base.
    2. The mbuf-pointer stash/cookie is never overwritten or invalidated.
    3. Physical address, buffer size, 'back', alignment and headroom stay
       consistent after any L2 adjustment.
    4. The WQE and packet buffer are each returned exactly once.
    5. No mbuf free/refill path simultaneously claims the same buffer.
    6. Command-buffer exhaustion cannot leave a modified but unsent frame
       to fall through to the normal receive path.

  Implement an isolated one-buffer RX-to-PKO forwarding experiment before
  pf integration. Inspect buffer identity before and after repeated pool
  recycling; combine ownership assertions with free-count accounting. When
  changing IPD first_mbuff_skip, recheck packet-cluster allocation size,
  alignment, and the driver arithmetic, not just the IPD register setting.

FINDING 3 -- Candidate pf_state pointers require explicit lifetime safety
             [HIGH]
  Affects: sections 4.2-4.4; Phase 1 steps 9-14.

  The plan stores raw pf_state pointers in mbuf packet metadata in PF_IN and
  PF_OUT, then dereferences them later in cnmac_start(). pf_test() may have
  dropped its reference before that transmit path runs. Concurrent state
  removal or 'pfctl -F states' can free a candidate first, producing a
  use-after-free. SMR protection for flow objects does not automatically
  protect the pf_state objects they reference.

  Safer approaches:
    - Prefer copying the immutable candidate/tuple fields and stable state
      identifiers into packet metadata, followed by safe state revalidation
      immediately before publishing the learned flow; OR
    - Take and retain explicit state references with complete release paths
      for mbuf drops, copies, replacement, destruction and TX completion.

  Define and document ownership of f_st[] through GC/teardown, including
  exactly which lock/reference protects each read. Inspect pfvar_priv.h as
  well as pfvar.h for the internal state definition at the pinned commit.

FINDING 4 -- Cached egress L2 and route information can become stale [HIGH]
  Affects: sections 4.2-4.3, 4.6.

  Storing the final destination/source MAC and physical egress interface in
  f_l2[] is efficient but requires invalidation. A pf state can remain alive
  after a route changes, an ARP/ND neighbor mapping changes, or an egress
  interface is reconfigured. Checking only that the link is up is not enough.

  Required design:
    - Tie flow validity to a forwarding generation / invalidation scheme.
    - Invalidate on relevant route changes, ARP or IPv6 neighbor changes,
      and physical/logical interface changes (including MTU changes).
    - Check validity during learn and again at lookup. A stale entry must
      fall back to ordinary forwarding, not transmit using a stale L2 header.
    - A conservative global flow-table flush is acceptable initially for
      this three-port private fork; refine only if profiling requires it.

FINDING 5 -- pf_pkt_addr_changed() candidate clearing conflicts with learn
             [HIGH]
  Affects: section 4.2; Phase 1 steps 9-12.

  Step 9 proposes resetting flow candidate data in pf_pkt_addr_changed(),
  but the outbound state-match path can call that routine during normal
  forwarding. It may erase the PF_IN candidate before the final TX frame
  reaches flow_learn(), so apparently eligible flows never learn.

  Required design: distinguish initialization of candidate metadata from
  invalidation after unsupported address transformations. Preserve the
  ingress candidate through the expected PF_IN -> PF_OUT path; reject it
  when a transformation makes the candidate invalid. Use shadow mode to
  validate the entire metadata lifecycle before enabling a bypass.

FINDING 6 -- PKO locking plan conflicts with R7 [HIGH FOR DESIGN CONSISTENCY]
  Affects: section 4.4; R7; Phase 2 step 18.

  R7 promises no locks except SMR on the hit path, while the shared PKO
  command-submission approach requires a per-egress lock. Also, reserving
  space before editing a packet must account for CMD pool allocation and
  command-buffer rollover, not just a nominal slot count.

  Recommendation: first use a bounded per-egress PKO mutex for both normal
  and fast submissions. Amend R7 to allow that lock. Verify whether the
  CN50xx can configure a genuinely separate output queue and command
  buffer before pursuing a lock-free dedicated-queue design. This is an
  optimization, not a prerequisite for functional zero-copy forwarding.

FINDING 7 -- Eligibility does not yet cover every pf side effect [HIGH]
  Affects: sections 4.3, 4.6; R3-R4.

  A fast-path hit bypasses more than address translation: normal pf packet
  processing can include per-packet rate limits, scrub behavior, TCP
  sequence/window checks, source tracking and updates to rule, source-node,
  table or match statistics. Updating s->expire and the state's byte/packet
  counters alone does not reproduce all of those effects. Bypassing ordinary
  TCP data packets also bypasses pf's normal sequence/window validation;
  trapping SYN/FIN/RST does not restore that validation.

  Required design:
    - Explicitly document the behavioral contract for offloaded TCP/UDP.
    - Expand the refusal predicate for unsupported per-packet pf features,
      including rate-limited or scrubbed states and source tracking where
      accurate per-packet accounting or policy checks are required.
    - Make explicit opt-in via a rule marker/tag the initial policy default
      rather than automatically offloading every apparently eligible state.
    - Verify direction-specific state accounting and pflow behavior against
      the chosen pf revision; document any deliberate differences.

FINDING 8 -- Packet parser and hash-key validation need stricter boundaries
             [MEDIUM/HIGH]
  Affects: sections 4.2-4.3; Phase 2 step 19; Phase 3 steps 24-26.

  IP_BUFS==1 alone does not guarantee that complete L2, IP, and TCP/UDP
  headers fit within the WQE packet length. Validate lengths before every
  dereference: optional VLAN/PPPoE header sizes, IPv4 IHL and total length,
  IPv6 payload length, L4 minimum length, TCP data offset and encapsulation
  length consistency. Ensure checksum and parse flags correspond to the
  actual packet format being handled.

  Distinguish an untagged frame from a priority-tagged VLAN 0 frame; using
  'vlan=0' for untagged collides with VID 0. Initialize the complete key
  storage, including padding and inactive union bytes, before hashing or
  comparing it. Malformed or unexpected packets must return to the slow
  path unchanged.

A.3 REVISED IMPLEMENTATION CHECKPOINTS
--------------------------------------

  Phase 0A: Pin exact -current commit; audit shared RX-group processing,
            PKO queue topology, WQE fields, FPA ownership, memory barriers.
            EXIT: hardware and driver assumptions written down.

  Phase 0B: Run standalone single-buffer RX -> PKO -> FPA recycling tests.
            EXIT: repeated buffer identity, ownership and pool accounting
            hold with no pf or NAT code involved.

  Phase 1A: Implement flow table, invalidation, safe candidate metadata,
            and shadow lookup; no actual forwarding shortcut.
            EXIT: key, translation and teardown checks pass under load.

  Phase 1B: Implement and measure mbuf-based software forwarding.
            EXIT: routing, NAT, reverse flows, state counters, exception
            fallback and state flush behave as explicitly specified.

  Phase 2A: Implement zero-copy plain IPv4 routing (no NAT).
            EXIT: correct checksum/TTL behavior and stable buffer counts.

  Phase 2B: Add IPv4 NAT and pf state synchronization.
            EXIT: exact translation, safe state teardown and no stale L2.

  Phase 2C: Add IPv6 routing and translation, with checksum/hop-limit tests.
            EXIT: correct behavior for eligible packets and clean fallback
            for unsupported extension headers.

  Phase 3 : Add VLAN / PPPoE and headroom changes only after the base path
            is proven; rerun buffer and alignment invariants.

  Phase 4 : Exercise faults and concurrent changes; endurance soak.
            EXIT: repeatable recovery, no ownership leaks and reliable
            mixed-traffic forwarding for days.

A.4 ADDITIONAL ACCEPTANCE TESTS
------------------------------

  Forwarding invalidation:
    - Replace a default route during sustained offloaded traffic.
    - Change an ARP/ND next-hop MAC and an egress interface or MTU.
    - Confirm stale flows stop bypassing and new traffic is revalidated.

  Buffer and command accounting:
    - Force packet-pool and command-pool pressure and rollover.
    - Check free counts AFTER traffic drains, as well as during load.
    - Track buffers owned by PKO and mbufs awaiting normal TX completion.
    - Verify the baseline accounting is restored after each test.

  Concurrency and packet ordering:
    - Bidirectional traffic over both cores with simultaneous state flushes,
      route changes, link flaps, ruleset reloads and net.flow.mode toggles.
    - Check that switching a flow between fast and slow paths does not
      introduce unexpected reordering or use freed flow/state objects.

  Packet correctness:
    - Truncated frames and headers, malformed TCP offsets and padding.
    - IPv4 UDP zero checksum; IPv6 UDP checksum; TTL/hop limit=1.
    - VLAN 0, unexpected/double VLAN, PPPoE length and protocol mismatch.
    - Frames that fail validation must enter the slow path UNMODIFIED.

  Endurance:
    - At least one 24-hour mixed-traffic soak and one 72-hour reliability
      run, including idle/active transitions and state cleanup.
    - Require zero unexplained FPA drift, double frees, crashes or stale
      forwarding after configuration changes.

A.5 BENCHMARK AND DOCUMENTATION NOTES
-------------------------------------

  - Retain >900 Mbit/s large-packet NAT and >100 kpps 64-byte UDP as
    engineering targets, not guaranteed outcomes. Measure baseline and
    modified behavior on the SAME kernel fork and test equipment.
  - Keep software-mode throughput and zero-copy throughput separate from
    reference OpenWrt measurements; annotate packet sizes and directions.
  - Explicitly document which pf behavior remains exact and which is
    deliberately sacrificed by the fast path (especially TCP validation,
    per-packet limits, statistics and synchronization).
  - Point build instructions and code references to the pinned OpenBSD
    checkout rather than relying on an older third-party source mirror.
  - Keep fail-safe net.flow.mode=0 and a known-good boot image testable
    independently of the new code.

A.6 FINAL DISPOSITION
---------------------

GO for Phase 0 hardware verification, ownership experiments and shadow-mode
control-plane work. NO-GO for integrated zero-copy forwarding until findings
1-6 have concrete design answers and testable invariants; finding 7 must be
covered by conservative eligibility and an explicit behavior contract, and
finding 8 by robust bounds checks.

Nothing here invalidates the overall project. The distinction is between
passing a throughput benchmark and being safe to forward continuously after
state, route, neighbor, interface and concurrency conditions change.

B.2.5 Behaviour contract and eligibility (F7)
  Contract for an offloaded flow (documented in the fork README):
  - pf sees SYN, FIN, RST, every packet before ESTABLISHED/MULTIPLE,
    fragments, ICMP, and everything in 4.7. pf does not see established
    TCP data or UDP payload packets of an offloaded flow; no sequence or
    window validation, no per-packet rule evaluation, no match-rule
    side effects for those packets.
  - State expire and state/rule packet and byte counters are refreshed
    by the GC within net.flow.gc seconds. Table and source-node
    per-packet statistics are not maintained for offloaded packets.
  Additional refusals in pf_state_offloadable():
  - rule has max-pkt-rate
  - rule scrub includes reassemble tcp (pf_normalize_tcp_stateful)
  - state has a source node with per-packet obligations (overload,
    max-src-conn-rate tracking); plain sticky-address is fine
  - rule has set delay / set prio / queue in zero-copy mode (unchanged)
  Policy default flips to opt-in: net.flow.policy=1, offload only when
  s->tag equals the id of a configured marker tag (pf "tag OFFLOAD" on
  the rule; no parser change). policy=0 remains available for benches.
  Refresh (4.3) also adds deltas to s->rule.ptr->packets[dir] and
  bytes[dir] under the rule's counter lock so pfctl -vsr stays usable.

B.2.6 Parser and key hygiene (F8)
  - Before every dereference: len >= l2len + 20 (v4) / 40 (v6);
    ihl == 5 and ip_len <= len - l2len; v6 payload_len consistent;
    L4: len >= ipoff + ihl*4 + 20 (TCP) / 8 (UDP); th_off >= 5 and
    th_off*4 <= remaining. PPPoE: length field == remaining - 6 and
    PPP proto in {0x0021, 0x0057}. Anything else: slow path, untouched.
  - struct flow_key gets a flags byte with VLAN_PRESENT; VID 0
    (priority tagged) is then distinct from untagged. Keys are memset
    to zero before fill (union and padding bytes are hashed).
  - IP_LE is only trusted when IP_TU is set and the packet is not a
    zero-checksum IPv4 UDP datagram.

B.2.7 Mode switching (not in the review)
  - Any change of net.flow.mode flushes the flow table and waits one SMR
    grace period before the new mode takes effect. Buffers already
    handed to PKO are unaffected (PKO frees them to the pool either way).

      path byte-for-byte unmodified.

C.2 EFFECT ON HOOK A AND THE RX PATH
-----------------------------------

Before the change:
  - cnmac_intr(void *arg) receives a cnmac_softc for a physical port.
  - The driver establishes a port-specific POW interrupt and checks
    that a received WQE's input port matches sc->sc_port.
  - Received mbufs are handed to if_input() in a per-interrupt batch.

After the change (as shown in the reviewed source diff):
  - cnmac_intr(void *arg) receives struct cnmac_rx_group *crg.
  - Each RX group has a POW interrupt and per-port receive batches.
  - The physical port is decoded from the WQE and resolved through
    cnmac_port_softc[port].
  - Normal received packets are delivered via ifiq_input() to the
    selected input queue, not the earlier if_input() path.

The relevant port-resolution sequence is:

  port = (work[1] & PIP_WQE_WORD1_IPRT) >> 42;
  if (port >= nitems(cnmac_port_softc) ||
      (sc = cnmac_port_softc[port]) == NULL)
          goto wqe_error;        /* schematic: preserve real error path */

  /* HOOK A: try fast path with the resolved physical-port softc here,
   * before cnmac_recv(sc, work, &crg->crg_rx_batch[port]). */

The fast-path hit must consume/return the WQE exactly once, submit or
otherwise account for the packet buffer, avoid normal receive batching,
and avoid incrementing the count of mbufs requiring replenishment.
A rejected packet must continue through cnmac_recv() unchanged (R16).

The Appendix B.2.1 proposal to resolve ingress from the WQE and use a
port-to-softc table is already compatible with this architecture.
Do not assume that all packets from one physical port are handled by
one CPU; counters and flow lifetime rules must tolerate concurrency.

C.3 OCTOBER 23, 2026 INTERRUPT-AFFINITY CHANGE
-----------------------------------------------

A separate OpenBSD commit on 2026-10-23 changed octciu.c:

  "sys/octeon: span work queue interrupts across CPUs"
  Commit: 65a9769
  https://github.com/openbsd/src/commit/65a9769

It restores assignment of work-queue interrupts across CPUs when
MULTIPROCESSOR is enabled, using:

  if (IS_WORKQ_IRQ(irq))
          cpuid = irq % ncpus;

updates, teardown and PKO submission path. It does NOT independently
prove any particular runtime mapping of a flow or port to a core;

D.3 CONSEQUENCES APPENDIX C DOES NOT DRAW
-----------------------------------------

  1. RE-BASELINE FIRST. The 172/229 Mbit/s figures (May 2025) predate
     RX queues. With ifiq_input() the slow path can use both cores for
     multi-flow traffic, so the gap this fork closes may be far smaller
     than sections 1 and 5 assume. Step 7 must measure, on the pinned
     kernel: single-flow routed NAT, 8-flow routed NAT, 64-byte pps,
     and per-core CPU. Add an explicit GO/NO-GO after step 7: if the
     multi-flow slow path already approaches the wire, the fork's payoff
     is single-flow throughput and pps only, and R10/R11 are restated
     against the measured baseline before any further work.

  2. FLOW-TO-CORE AFFINITY IS A PIP PROPERTY. One direction of a flow
     always hashes to one tag, hence one group, hence one core. The
     forward and reverse directions of a connection will generally land
     on different cores (CRC-style tags are not symmetric in src/dst).
     Consequences: flow entries are effectively single-writer per
     direction (good cache locality, no design reliance on it); the two
     directions touch the same two pf states from two cores, so the
     refresh path and f_st[] handling must be MP-safe (B.2.2 already
     requires this); the per-egress PKO mutex (B.2.4) is contended by
     exactly the other core plus the ifq TX path.

  3. COUNTERS. Use counters(9) (per-CPU, lock-free, counters_add /
     counters_read) for f_pkts, f_bytes and all kstat counters instead
     of 64-bit atomics. It is the OpenBSD idiom and removes C.4's
     "verify 64-bit atomics on octeon" question (they do exist, via
     lld/scd, but counters(9) is cheaper and already MP-correct).

  4. POW TAG DISCIPLINE. The fast path must consume the WQE inside the
     same get-work loop that cnmac_recv() uses and must not hold a WQE
     across the next work request; the existing tag-switch sequence
     (cn30xxpow_tag_sw_wait / work_request_async) is kept unchanged.
     The ORDERED tag type serializes a tag's work on one core at a
     time, which gives the hit path per-flow in-order delivery for free.

  5. BOUNDED REORDERING AT THE FAST/SLOW BOUNDARY. Hits leave through PKO
     immediately; misses are batched to an ifiq and processed later by
     softnet. At learn time the first hit can overtake the last slow-path
     packet of the same flow; at teardown the FIN takes the slow path
     while preceding data went fast. This is inherent (the Linux
     flowtable has the same property) and TCP tolerates it. Add it to
     the behaviour contract (B.2.5). The A.4 ordering test must expect
     reordering only at transitions and never in steady state.

  6. REFILL ACCOUNTING IS PER RX GROUP. A hit must not be counted toward
     that group's mbuf refill. The PKT pool depth shrinks transiently by
     the number of packets in flight to PKO (bounded by the PKO queue
     depth), which is not a leak. Phase 0B must record the in-flight
     count so FPA free counts can be interpreted (A.4 already asks for
     this; this is why).

  7. IFF_RUNNING. cnmac_recv() drops work for a port that is not
     running. The fast path must check IFF_RUNNING on both the ingress
     and the egress softc before touching the frame (R16).

  8. MODE 1 (software hit path). Set m_pkthdr.ph_flowid from the WQE tag
     as the driver now does, and bypass crg_rx_batch[port] for hits;
     ifq_enqueue() on the egress ifp directly.

  9. GROUP COUNT. Record cnmac_rx_groups and the actual group-to-CPU
     mapping on the two-core CN5020 in Phase 0A. If groups == ncpus,
     each core owns one group; if groups > ncpus, cores interleave. This
     affects tuning (per-core flow cache footprint), not the design.
